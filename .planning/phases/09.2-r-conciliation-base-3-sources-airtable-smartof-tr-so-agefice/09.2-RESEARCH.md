## Summary

Cette phase ne construit **rien de neuf** : elle rejoue dans le bon ordre 9 scripts existants, écrit 1 test comportemental (`dedupe.merge.test.ts`), arbitre les conflits en CSV, et prouve la chaîne closure sur 1 session témoin. La recherche a cartographié le comportement RÉEL de chaque script (clés de matching, ce qu'ils mutent, idempotence, invocation).

**Trois écarts code↔contrat ont été trouvés et doivent piloter le plan :**

1. **Doublon de matchers Tréso** : il existe DEUX scripts qui écrivent les booléens AGEFICE, sur DEUX jeux de colonnes Prisma différents et coexistants. `match-treso-agefice.ts` (apps/web) écrit le jeu canonique lu par l'UI (`factureEnvoyee/validationOpco/remboursementOpco/paiementClient`) ET corrige `priceHT`. `import-treso-agefice.ts` (packages/db) écrit l'AUTRE jeu (`invoiceSent/opcoApproved/opcoReimbursed/paymentReceived`), que l'UI tréso ne lit PAS comme statuts principaux. → Le rejeu Tréso de E2 doit passer par `match-treso-agefice.ts`, pas `import-treso-agefice.ts`.

2. **Le bug §4 est dans `match-treso-agefice.ts`** : le montant EST aujourd'hui un critère d'entrée du scoring (`+20 si montant ±5 %`, lignes 247-250), exactement ce que §4 interdit. La clé d'entrée actuelle est nom-stagiaire(+50)/dates(+30/+20)/montant(+20)/opco(+10), pas `dates+org+nbStagiaires`. C'est l'unique modification de script justifiée par écrit que la phase devra acter (§0/§7c).

3. **ZÉRO test d'intégration BDD réelle dans tout le repo** (941 tests, tous mockent Prisma — confirmé par le commentaire de `packages/db/vitest.config.ts`). Le contrat exige `dedupe.merge.test.ts` qui prouve une fusion réelle. C'est le point d'architecture le plus incertain : introduire un test contre une vraie base (ou rollback de transaction) sera une PREMIÈRE dans ce projet.

**Primary recommendation :** Ordonner E2 = `prisma generate` → écrire `dedupe.merge.test.ts` (approche transaction-rollback sur la base de dev, voir Validation Architecture) → dedupe dry/apply → import-from-smartof dry (tranche le backfill lieu) /apply → sync-smartof-prices → match-treso-agefice (après correction §4) + backfill-trainer. Gate E3 via script de comparaison CA dédié (2 niveaux). E4 via `e2e:closure` + assert `rawJson.source !== 'stub'`.

### 1. `apps/web/scripts/dedupe.ts` — fusion orgs/persons
**⚠️ Localisation** : `apps/web/scripts/dedupe.ts`, PAS `packages/db/scripts/` comme indiqué dans CONTEXT/RECONCILE §0 (référence à corriger côté plan).

**3 détections** (lignes 272-396) :
- `detectOrgsBySiret` (274) : groupe les orgs par SIRET identique, MAIS ne dédupe QUE si les noms se ressemblent (includes / ≥2 tokens communs, lignes 290-309). **SIRET partagé entre noms différents ⇒ écarté de l'auto-merge** — conforme garde-fou §3.2 (ces cas tombent en reliquat E3, le script ne les touche pas).
- `detectEiSelfOrgsPerPerson` (321) : pour 1 Person, plusieurs orgs `EI_SELF` dont le nom contient ≥1 token nom/prénom → doublon EI probable.
- `detectPersonsByName` (365) : bucket par `nom+prénom` normalisé (avec inversion). **Garde-fou email** lignes 385-388 : si tous les candidats ont des emails TOUS différents ET non-null → SKIP (probable 2 vraies personnes). **L'email n'est jamais clé de fusion seule** — conforme §3.2. ⚠️ Subtilité : le guard ne se déclenche que si TOUS les candidats ont un email ET qu'ils sont tous distincts ; un groupe `email partagé + noms identiques` fusionne (c'est voulu), mais le cas Nestenn (`email partagé + noms DIFFÉRENTS`) ne tombe jamais dans `detectPersonsByName` car le bucketing est par nom — donc pas de risque de fusion par email seul. **Confirmé : pas de risque de fusion par email seul.**

**Choix du canonique** : `pickCanonical` (103) trie par score. `scoreOrg` (57) = smartof×1000 + airtable×100 + agefice×10 + invoice×5 + participant×3 + legalLink. `scorePerson` (80) = smartof×1000 + airtable×100 + sensitive×50 + participant×5 + trainer×5 + legalLink. → SmartOF prioritaire, conforme golden-record §2.

### 2. `apps/web/scripts/import-from-smartof.ts` — identité/sessions/inscriptions

**🔑 RÉSOLUTION DU LIEU (clé pour les 22 sessions sans lieu)** : `resolveSessionLocation` (769-802). JOIN "SessionParticipant" sp ON sp."sessionId" = s.id
JOIN "Organization" o ON o.id = sp."sponsorOrgId" AND o."opcoCode" = 'AGEFICE'

ORDER BY p."durationHours" DESC, nb_with_sensitive DESC;

## Common Pitfalls

### Pitfall 1 : Le mauvais matcher Tréso écrit dans le vide
**Ce qui va mal** : lancer `import-treso-agefice.ts` met à jour `invoiceSent/opcoApproved/...` que l'UI tréso (`treso-status-block.tsx`, `audit-treso/page.tsx`, `treso-formulas.ts`) ne lit PAS comme statuts principaux — les pastilles restent grises malgré l'apply.
**Pourquoi** : la table SessionParticipant a DEUX jeux de booléens coexistants (schema lignes ~640-665). L'UI lit `factureEnvoyee/validationOpco/remboursementOpco/paiementClient`. Seul `match-treso-agefice.ts` écrit ce jeu.
**Éviter** : E2 utilise `match-treso-agefice.ts`. Acter par écrit que `import-treso-agefice.ts` est écarté.
**Signal** : après apply, requête SQL `SELECT count(*) FROM "SessionParticipant" WHERE "factureEnvoyee"` ne bouge pas.

### Pitfall 2 : Montant comme critère d'entrée masque le bug prix
**Ce qui va mal** : le scoring actuel donne +20 quand le montant Tréso ≈ montant base. Or le montant base est FAUX (336 €). Un match qui "réussit" sur un montant faux conforte un mauvais rapprochement et empêche la correction.
**Éviter** : appliquer la correction §4 AVANT la passe Tréso (retirer montant de l'entrée, l'utiliser en départage seulement).
**Signal** : sessions à 336 € qui matchent "trop bien" leur ligne Tréso.

### Pitfall 3 : dry-run import-from-smartof ne révèle pas les lieux backfillables
**Ce qui va mal** : on s'attend (RECONCILE §1) à ce que le dry-run liste les lieux résolus ; or `resolveSessionLocation` renvoie null en dry-run (ligne 789) — aucun lieu affiché.
**Éviter** : script read-only éphémère qui pull `/api/session/list` et liste `custom_field_1/2/3` des 22 codes ; OU `--apply --only=sessions` après pg_dump puis compter `locationId` non-null.
**Signal** : "0 lieu proposé" en dry-run alors qu'on attend ≤9.

### Pitfall 4 : Prisma client absent → tout script crash au boot
**Ce qui va mal** : `Cannot find module '.prisma/client'` ou types manquants.
**Éviter** : `pnpm --filter @qualiof/db db:generate` en tout premier (Wave 0).
**Signal** : crash immédiat à l'import `@qualiof/db`.

### Pitfall 5 : import worker/auth dans un script tsx
**Ce qui va mal** : `react does not provide an export named 'cache'` (cf. mémoire `feedback_worker_no_react_imports`). closure-e2e-test.ts contourne déjà en répliquant la logique ZIP sans `auth.ts` (148-149).
**Éviter** : scripts E2/E3 n'importent jamais une server action utilisant `requireRole`/`validateRequest`.

### Pitfall 6 : Conflit booléen descendant silencieux
**Ce qui va mal** : OR-merge `false→true` ne remet jamais `true→false` — un statut base `true`/Tréso `false` reste `true` sans trace.
**Éviter** : audit SQL séparé en E3 listant `SP.factureEnvoyee=true` dont la ligne Tréso correspondante = NON → reliquat verdict manuel (§2).

### `dedupe.merge.test.ts` — approche recommandée : INTÉGRATION BDD RÉELLE par transaction-rollback

**Pourquoi PAS un mock** : le contrat (§3.2) exige de prouver qu'après fusion, les `ExternalIdentity` du perdant pointent vers le survivant. Un mock Prisma ne fait que vérifier qu'on a appelé `updateMany` avec les bons args — il ne prouve PAS que le repointage FK est cohérent ni que `mergePersons`/`mergeOrgs` n'oublie pas une table. Toute la valeur est dans l'exécution réelle.

**Pourquoi PAS testcontainers / pg-mem** : aucun n'est présent dans le repo (vérifié — 0 occurrence). Les introduire = nouvelle dépendance lourde + setup CI inexistant, contre l'esprit "zéro reconstruction" et le délai pré-audit.

**Approche retenue — transaction-rollback sur le Postgres de dev** :
1. Le test tourne dans `packages/db` (où vit le client Prisma) ou apps/web — recommandé `packages/db/scripts/__tests__/dedupe.merge.test.ts` car le script y est conceptuellement rattaché (malgré sa localisation apps/web — extraire `mergePersons`/`mergeOrgs` en export nommé depuis dedupe.ts pour les tester sans `main()`, exactement comme `import-veille-from-xlsx.ts` expose `persistVeilleRow`).
2. Wrapper chaque test dans une transaction Prisma rollback-only : `await prisma.$transaction(async (tx) => { /* seed 2 persons + ExternalIdentity sur le perdant ; mergePersons(tx, canonical, [dup]) ; assert ExternalIdentity repointé ; throw ROLLBACK })`. **Pré-requis** : `mergePersons`/`mergeOrgs` doivent accepter un `tx` injecté (aujourd'hui ils ouvrent leur propre `prisma.$transaction` en interne — petite refacto pour accepter un client transactionnel ; à justifier comme "rendre testable", pas comme "changer le mécanisme").
3. Alternative plus simple si l'injection de tx est trop invasive : base de test jetable seedée puis `prisma migrate reset --force` / suppression des lignes créées en `afterEach`. Plus lent, mais zéro refacto du script.

**Assertions minimales (RED→GREEN)** :
- Seed : Person A (survivant, +SmartOF identity) + Person B (perdant) + `ExternalIdentity{entityType:'Person', entityId:B}`. Fusion → `ExternalIdentity` pointe vers A, Person B supprimée.
- Cas Org symétrique (ExternalIdentity entityType='Organization').
- Cas garde-fou : `detectPersonsByName` ne propose PAS de fusion pour 2 persons même nom + emails différents (test de la fonction de détection, mockable, pas besoin de BDD).

**Le test est écrit ET fermé dans E2** (ne devient pas un gate ouvert permanent ; il prouve l'invariant une fois pour autoriser la passe dedupe).
