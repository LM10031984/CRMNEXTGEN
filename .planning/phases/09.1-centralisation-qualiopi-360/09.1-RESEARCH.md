## Architecture Decisions to Make Explicit

### Decision A — Data Model JSON Shape `SessionParticipant.docStatus`

**Locked** : Json sur `SessionParticipant` (D-07). Voici la shape exacte recommandée :

```ts
// packages/shared/src/schemas/qualiopi-matrix.ts (à créer)
import { z } from 'zod';
import { DocType } from '@qualiof/db';  // enum Prisma

export const DocStatusState = z.enum(['GENERATED', 'MANUAL_OK', 'MISSING']);
export type DocStatusState = z.infer<typeof DocStatusState>;

export const DocStatusEntrySchema = z.object({
  state: DocStatusState,
  // Optionnel : présent si MANUAL_OK + admin a uploadé le PDF signé scanné.
  // Pas de FK Document — c'est une key MinIO directe (cohérent avec
  // SensitiveData.* keys et Person.ribKey patterns).
  uploadedSignedPdfKey: z.string().optional(),
  uploadedSignedAt: z.string().datetime().optional(), // ISO 8601
  uploadedByUserId: z.string().uuid().optional(),
  // Cas D-01 dérogatoire : coché MANUAL_OK SANS uploadedSignedPdfKey
  // → la matrice affiche pastille orange "preuve manquante".
  markedOkWithoutUpload: z.boolean().optional(),
  // Note libre admin (raison dérogation, etc.)
  note: z.string().max(500).optional(),
  updatedAt: z.string().datetime(),
});
export type DocStatusEntry = z.infer<typeof DocStatusEntrySchema>;

// Map clé=DocType, valeur=entry. Stocké dans SessionParticipant.docStatus.
// Prisma Json? = null|undefined si jamais coché.
export const DocStatusMapSchema = z.record(z.string(), DocStatusEntrySchema);
export type DocStatusMap = z.infer<typeof DocStatusMapSchema>;
```

**Pourquoi cette shape** :
- `state` discriminé strict (pas de string libre)
- `uploadedSignedPdfKey` séparé de `state` → on peut avoir MANUAL_OK + uploadedPdf, OU MANUAL_OK + markedOkWithoutUpload (warning pastille orange D-06)
- Pas de `pdfUrl` direct → on stocke la clé MinIO et on signe à la demande (cohérent `Document.pdfUrl`)
- `updatedAt` ISO string (Json ne supporte pas Date natif Prisma)

**Lecture matrice** (algo de dérivation 3 états):

```ts
function deriveCellState(
  docType: DocType,
  participant: { docStatus: DocStatusMap | null },
  documents: Map<string, { id: string; pdfUrl: string }>,   // participant docs indexed by type
  productDocs: Map<string, { id: string; pdfUrl: string }>, // PROGRAMME, DEROULE_PEDAGOGIQUE (session-wide)
  sessionDocs: Map<string, { id: string; pdfUrl: string }>, // GRILLE_OBS_SESSION, CHECKLIST_FORMATION
  pedagogicalAssets: Map<string, { id: string; pdfUrl: string | null }>,
): { state: DocStatusState; pdfRef?: { kind: 'document'|'asset'|'productDoc'|'sessionDoc'; id: string }; warning?: 'no_proof' } {
  const manual = participant.docStatus?.[docType];

  // Cas dérogatoire D-01 : coché OK sans upload → pastille orange
  if (manual?.state === 'MANUAL_OK' && manual.markedOkWithoutUpload) {
    return { state: 'MANUAL_OK', warning: 'no_proof' };
  }

  if (manual?.state === 'MANUAL_OK' && manual.uploadedSignedPdfKey) {
    // PDF signé uploadé — pastille verte, lien vers le signé
    return { state: 'MANUAL_OK' };
  }

  // Sinon on regarde si un Document/Asset/PartagéProd existe pour ce type
  // Priorité : participant doc > pedagogical asset > session-wide > product-wide
  const partDoc = documents.get(docType);
  if (partDoc) return { state: 'GENERATED', pdfRef: { kind: 'document', id: partDoc.id } };

  const asset = pedagogicalAssets.get(mapDocTypeToPedKind(docType));
  if (asset?.pdfUrl) return { state: 'GENERATED', pdfRef: { kind: 'asset', id: asset.id } };

  const prodDoc = productDocs.get(docType);
  if (prodDoc) return { state: 'GENERATED', pdfRef: { kind: 'productDoc', id: prodDoc.id } };

  const sessDoc = sessionDocs.get(docType);
  if (sessDoc) return { state: 'GENERATED', pdfRef: { kind: 'sessionDoc', id: sessDoc.id } };

  return { state: 'MISSING' };
}
```

### Decision C — Worker Extension (mode `single-participant`)

**Bonne nouvelle** : le worker n'a **pas besoin** d'être modifié. Sa logique traite déjà 1 job = 1 participant × 1 kind. C'est `generateClosurePack` (server action) qui prend déjà un paramètre `participantIds?` et qui doit gagner un paramètre `kinds?`.

**Diff conceptuel** :

```diff
// apps/web/src/server/actions/closure-pack.ts
 export async function generateClosurePack(
   sessionId: string,
-  options?: { participantIds?: string[] },
+  options?: { participantIds?: string[]; kinds?: ClosureDocKind[] },
 ): Promise<{ ok: boolean; batchId?: string; ... }> {
   // ...
   // Construit la liste des jobs à créer en filtrant les kinds déjà faits.
+  const kindsToProcess = options?.kinds ?? CLOSURE_DOC_KINDS;
   const jobsToCreate = session.participants.flatMap((p) => {
     const done = alreadyDoneByParticipant.get(p.id) ?? new Set<ClosureDocKind>();
-    return CLOSURE_DOC_KINDS.filter((kind) => !done.has(kind)).map((kind) => ({...}));
+    return kindsToProcess.filter((kind) => !done.has(kind)).map((kind) => ({...}));
   });
```

⚠️ **Subtilité importante** : en mode `single-participant + kinds: [X]`, on **doit forcer** la régénération même si déjà présent. Sinon `alreadyDoneByParticipant` skip l'unique kind demandé et renvoie `alreadyComplete: true`. → ajouter un flag `force?: boolean` qui bypasse le skip-existing en mode mono :

```diff
+  if (isMonoMode && options?.force) {
+    alreadyDoneByParticipant = new Map(); // bypass skip
+  }
```

Avec `force: true` la regen écrase l'asset (via `pedagogicalAsset.upsert` déjà en place dans le worker) ou crée un nouveau `Document` (sha256 différent du précédent).

### Decision D — Refresh Strategy

Le worker tourne async, donc l'UI ne voit pas immédiatement le résultat. Patterns à utiliser :

- **Régénération mono-doc** : afficher toast `sonner` "Génération lancée — refresh dans 30s" + `router.refresh()` immédiat (la cellule passe en pastille `RUNNING` grise temporaire), puis polling via `BatchProgressAutoRefresh` (déjà en place) qui auto-refresh la fiche session quand le batch est COMPLETED.
- **Re-gen Convention/AGEFICE** (synchrone, pas BullMQ) : `await generate...()` puis `router.refresh()` + toast success. Pattern déjà en place dans `ParticipantActionsMenu`.
- **Upload signé** : multipart FormData → server action → `revalidatePath('/app/sessions/${id}')` + `router.refresh()`. ~2s round-trip.
- **markDocStatus** (checkbox/select) : `useTransition` + optimistic state local côté client, puis `router.refresh()`.

Polling existant `BatchProgressAutoRefresh` poll toutes les 2s tant que `status ∈ {PENDING, RUNNING}` → réutilisable.

### Decision E — Resolution du Bug P0 « Programme dupliqué N fois »

**Cause racine actuelle** (vérifiée dans `apps/web/src/app/app/sessions/[id]/page.tsx:107`) : Le code charge `Document.entityType='product'` (1 fichier session-wide) et l'expose dans `productDocByType` — mais l'audit UX comptait `Document.entityType='participant'` pour le statut Programme remis ?, ce qui forçait soit la duplication des PDF, soit le N "manqué".

**Résolution structurelle dans 9.1** :
1. Le PDF Programme reste **1 seul** `Document(entityType='product', entityId=productId)` — déjà OK aujourd'hui.
2. La matrice affiche N **lignes** Programme (1 par participant) — **chaque cellule lit le même `pdfRef` partagé** (lien vers le doc produit).
3. Le **statut** "remis ?" par participant vit dans `SessionParticipant.docStatus['PROGRAMME'] = { state: 'MANUAL_OK', ... }`.
4. Le booléen legacy `SessionParticipant.programmeDelivered` est **shadowed** : si `docStatus['PROGRAMME']` existe, il prend priorité. Migration douce : pas de delete legacy, juste preference rule. Possibilité backfill à terme (Phase 10+) mais hors scope 9.1.

**Bénéfice** : 0 duplication PDF, 0 confusion UI, statut par-participant cohérent.

```ts
// apps/web/src/lib/use-local-storage-state.ts
'use client';
export function useLocalStorageState<T>(key: string, initial: T): [T, (next: T) => void] {
  const [state, setState] = useState<T>(initial);
  const [hydrated, setHydrated] = useState(false);
  useEffect(() => {
    try {
      const raw = window.localStorage.getItem(key);
      if (raw !== null) setState(JSON.parse(raw) as T);
    } catch { /* private mode, fallback initial */ }
    setHydrated(true);
  }, [key]);
  const set = useCallback((next: T) => {
    setState(next);
    try { window.localStorage.setItem(key, JSON.stringify(next)); } catch { /* ok */ }
  }, [key]);
  return [hydrated ? state : initial, set];
}
```

## Common Pitfalls

### Pitfall 1 — Skip-existing bypass pour mode mono

**What goes wrong:** L'utilisateur clique "Re-générer QCM pour Justine" mais le QCM existe déjà → `generateClosurePack` retourne `alreadyComplete: true` sans rien régénérer. Frustration totale.

**Why it happens:** Le code existant skip les kinds déjà présents en mode mono (lignes 130-174 closure-pack.ts). C'est le bon comportement pour pack global, mais l'inverse de ce qu'on veut pour re-gen ciblée.

**How to avoid:** Ajouter un flag `force?: boolean` à `generateClosurePack(sessionId, options)`. Si `force && isMonoMode && kinds?.length === 1` → bypass skip. Le worker écrasera via `pedagogicalAsset.upsert` (déjà en place).

**Warning signs:** Bouton "Re-générer" qui ne fait rien visible. Toast `{ alreadyComplete: true }` → c'est le bug.

### Pitfall 2 — Race condition `docStatus` Json patch

**What goes wrong:** 2 admins ouvrent la matrice. Admin A coche "Convention signée" pour Justine. Admin B coche "AGEFICE signée" pour Justine. Si les 2 actions ne sont pas atomiques, B écrase la modif de A (Prisma lit le docStatus complet, mute en mémoire, write back).

**Why it happens:** Json patch en Prisma 5.22 n'a pas de syntaxe atomique JSONB merge native. Le pattern naïf `update({ data: { docStatus: { ...participant.docStatus, [type]: newEntry } } })` est lecture-modif-écriture.

**How to avoid:** Utiliser `prisma.$transaction` + isolation `Serializable` (pattern `bumpAndFinalize` worker). Ou plus simple : `$queryRaw` Postgres `jsonb_set` :
```ts
await prisma.$executeRaw`
  UPDATE "SessionParticipant"
  SET "docStatus" = jsonb_set(COALESCE("docStatus", '{}'), '{${docType}}', ${JSON.stringify(entry)}::jsonb)
  WHERE id = ${participantId} AND "sessionId" IN (SELECT id FROM "TrainingSession" WHERE "tenantId" = ${tenantId})
`;
```
Le `tenantId` filter dans le subselect protège du cross-tenant (vérification stricte).

**Warning signs:** Tests parallèles qui passent un par un mais cassent en concurrence. Audit qui montre 2 actions consécutives où la 2e a écrasé la 1ère.

### Pitfall 3 — Filtres matrice cross-tenant

**What goes wrong:** Le filtre "Statut OPCO" requête `prisma.organization.findMany` pour la liste des opcoCode. Si on oublie le `tenantId` scope, on liste des codes d'autres tenants.

**How to avoid:** Toujours `tenantId: user.tenantId` dans toute query. Convention CLAUDE.md.

**Warning signs:** Dropdown avec valeurs étranges qui n'existent pas dans la session courante.

### Pitfall 4 — Composant client avec props non-sérialisables

**What goes wrong:** Passer une fonction-composant (`Icon: typeof LucideIcon`) ou un objet Prisma avec Date d'un Server Component à un Client Component → erreur Next.js 14.

**Why it happens:** RSC boundary serialization strict.

**How to avoid:** Pattern `CollapsibleSection.icon` (passer un ReactNode déjà instancié `<MyIcon className="..." />`, pas la fonction). Dates → ISO strings. Decimals Prisma → `.toString()` ou `Number(...)`.

**Warning signs:** Erreur runtime "Functions cannot be passed directly to Client Components".

### Pitfall 5 — Émargement multi-jours agrégé

**What goes wrong:** D-12 dit "1 cellule agrégée Émargement par participant". Si on calcule l'agrégé en lecture page server, et qu'un slot manque pour 1 demi-journée sur 4, la cellule devient ambiguë (partiellement signé ?).

**How to avoid:** Définir explicitement la règle d'agrégation :
- `EMARGEMENT` cell `GENERATED` ssi `PedagogicalAsset` EMARGEMENT existe pour ce participant
- `EMARGEMENT` cell `MANUAL_OK` ssi `Attendance` row existe pour TOUS les slots de la session ET tous ont `signedAt != null` ET `signatureUrl != null`
- Sinon `MISSING`
- Cas partiel (X/Y signés) → afficher `MISSING` avec tooltip "X/Y demi-journées signées" + drawer détail D-12

**Warning signs:** Émargements partiels affichés en vert alors qu'il manque des signatures.

### Pitfall 6 — `revalidatePath` qui ne refresh pas la matrice

**What goes wrong:** Server action retourne `{ ok }` + `revalidatePath('/app/sessions/${id}')` mais la matrice ne se met pas à jour côté client.

**Why it happens:** `revalidatePath` invalide le cache RSC, mais si le composant client n'écoute pas (pas de Suspense, pas de polling), le visiteur ne voit rien.

**How to avoid:** Combinaison : `revalidatePath` server + `router.refresh()` client après l'action. Pattern Phase 9 `LeadStatusSelect`.

**Warning signs:** Action exécutée (toast success), audit log écrit, mais l'UI montre encore l'ancien état.

### Pitfall 7 — Bug P0 régression : oublier `entityType='product'` lookups

**What goes wrong:** Programmer la matrice en oubliant que PROGRAMME a `entityType='product'` (1 PDF partagé) → la matrice cherche `Document(participantId=X, type='PROGRAMME')` → ne trouve rien → affiche MISSING pour tous, alors que le PDF existe au niveau produit.

**Why it happens:** Confusion entre "PDF stocké" (product-wide) et "statut par-participant" (docStatus Json).

**How to avoid:** Le helper `deriveCellState` (cf Decision A) gère explicitement la priorité : participant doc > pedagogical asset > session-wide > product-wide. Tester explicitement le cas PROGRAMME dans `__tests__/qualiopi-matrix.smoke.test.ts`.

**Warning signs:** Matrice avec colonne Programme entièrement rouge alors que le produit a un PDF Programme généré.

## Code Examples

### Example 1 — Server Action `markDocStatus`

```ts
// apps/web/src/server/actions/qualiopi-matrix.ts
'use server';

import { z } from 'zod';
import { revalidatePath } from 'next/cache';
import { prisma } from '@qualiof/db';
import { requireRole, UnauthorizedError, ForbiddenError } from '@/lib/rbac';
import { DocStatusState } from '@qualiof/shared';
import { logDocumentEvent } from '@/lib/audit-log'; // À créer (pattern logLeadEvent)

const MarkDocStatusInputSchema = z.object({
  participantId: z.string().uuid(),
  docType: z.string(), // DocType enum string
  state: DocStatusState,
  markedOkWithoutUpload: z.boolean().optional(),
  note: z.string().max(500).optional(),
});

export async function markDocStatus(input: z.infer<typeof MarkDocStatusInputSchema>): Promise<{ ok: boolean; error?: string }> {
  let user;
  try {
    user = await requireRole(['ADMIN', 'MANAGER']);
  } catch (e) {
    if (e instanceof UnauthorizedError || e instanceof ForbiddenError) return { ok: false, error: e.message };
    throw e;
  }

  const parsed = MarkDocStatusInputSchema.safeParse(input);
  if (!parsed.success) return { ok: false, error: 'Données invalides' };

  // Vérification tenant scope via SessionParticipant → TrainingSession.tenantId
  const participant = await prisma.sessionParticipant.findFirst({
    where: { id: parsed.data.participantId, session: { tenantId: user.tenantId } },
    select: { id: true, sessionId: true, docStatus: true },
  });
  if (!participant) return { ok: false, error: 'Inscription introuvable' };

  const current = (participant.docStatus ?? {}) as Record<string, unknown>;
  const before = current[parsed.data.docType] ?? null;
  const entry = {
    state: parsed.data.state,
    markedOkWithoutUpload: parsed.data.markedOkWithoutUpload,
    note: parsed.data.note,
    updatedAt: new Date().toISOString(),
  };

  await prisma.sessionParticipant.update({
    where: { id: parsed.data.participantId },
    data: { docStatus: { ...current, [parsed.data.docType]: entry } },
  });

  await logDocumentEvent({
    tenantId: user.tenantId,
    actorUserId: user.id,
    targetEntityId: parsed.data.participantId,
    action: 'documents.status_change',
    diff: { [parsed.data.docType]: { before, after: entry } },
  });

  revalidatePath(`/app/sessions/${participant.sessionId}`);
  return { ok: true };
}
```
