## Bug P0 Resolution

**Problème historique** : la matrice montrait le Programme « dupliqué N fois » dans l'UI (1 ligne par participant) avec un statut différent par-participant. Cela créait une confusion : « est-ce que le PDF est en N exemplaires en BDD ? Pourquoi un participant a Programme MISSING alors qu'un autre a Programme GENERATED ? »

**Solution structurelle livrée** :

1. **1 SEUL PDF stocké session-wide** : `Document.entityType='product'` + `entityId=productId` → 1 row en BDD pour le Programme partagé par tous les participants de la session.
2. **N statuts par-participant** dérivés via `SessionParticipant.docStatus Json?` (clé = DocType, valeur = state + uploadedSignedPdfKey?).
3. **Pure fn `deriveCellState`** orchestre la priorité de lecture :
   - **Priorité 1** : `participant.docStatus[docType]` (manual override par-participant : MANUAL_OK avec preuve PDF uploadée, OU MANUAL_OK markedOkWithoutUpload dérogatoire D-01)
   - **Priorité 2** : `participantDocs` (PDF générés par closure-pack pour ce participant — Convention, Émargement, Attestation, etc.)
   - **Priorité 3** : `pedagogicalAssets` per-participant si présents
   - **Priorité 4** : `sessionDocs` (PDFs session-wide spécifiques : Déroulé, Grille, Checklist)
   - **Priorité 5** : `productDocs` (1 PDF Programme session-wide partagé via productId)
4. **Anti-régression** : test unitaire ciblé `apps/web/src/lib/__tests__/derive-cell-state.test.ts:Test 1` commenté `// Bug P0 anti-régression` — vérifie que pour `docType='PROGRAMME'` avec `participant.docStatus=null` et un seul `productDocs` rempli, `deriveCellState` retourne `{ state: 'GENERATED', pdfRef: { kind: 'productDoc', id: 'doc1' } }`.

**Validation manuelle** : Flow Bonus du `09.1-SMOKE.md` documente la vérification visuelle (1 row `Document.entityType='product'` côté BDD, mais N cellules Programme avec statut indépendant par participant).

## Conventions Posées

Conventions reproductibles pour les futures phases (Phase 10+) :

1. **AuditLog `documents.*`** : 4 actions namespacées (regenerate / upload_signed / status_change / delete). Helper `logDocumentEvent` clone strict `logLeadEvent` Phase 9 — module isolé `lib/document-audit.ts` (NE PAS éditer `audit-log.ts` Phase 9). Pattern « one helper per entity » reproductible (`logSessionEvent`, `logInvoiceEvent`, etc.).
2. **localStorage key pattern** `qualiof-{feature}-{scopeId}` (ex. `qualiof-matrix-filters-{sessionId}`) — évite fuites cross-scope (R5 mitigation).
3. **Helper `useLocalStorageState` SSR-safe** réutilisable (Plans 04+ pour autres filtres persistants).
4. **`jsonb_set` raw atomique** : `prisma.$executeRaw(Prisma.sql\`UPDATE ... SET docStatus = jsonb_set(...)\`)` pour patch JSONB atomique côté Postgres (Pitfall 2 race mitigée). Pattern reproductible pour autres `Json?` columns évolutives.
5. **Server Component + Client shell séparés** : Server pré-dérive Map-heavy non-sérialisable (ex. CellState), propage props sérialisables (Array + primitive) au Client. Évite useState dans RSC tree. Pattern reproductible pour matrices Phase 10+ (audit Qualiopi 32 indicateurs).
6. **Smoke tests source-regex** (D-Phase9-N reproduit) : `vitest environment=node` + grep statiques `readFileSync` sur le source TSX. Pas de Testing Library installé. Couvre export name + props wiring + a11y attributes + lucide icons + palette UI-SPEC sans render runtime.
7. **Bulk fetch `Promise.all` parallèle** en haut de page Server Component : 4-5 queries Prisma indépendantes lancées en simultané pour éviter N+1 sur listings filles (participantDocs / productDocs / sessionDocs / pedagogicalAssets).
8. **Tenant-scope defense-in-depth** : `findFirst` tenant-scopé EN AMONT (court-circuit) + filtre raw SQL EN AVAL via sub-SELECT TrainingSession.tenantId (dernière ligne de défense Pitfall 3 cross-tenant).
9. **URL-state via Next.js App Router `searchParams` Promise** (Next 14.2+) — pattern reproductible pour Phase 10 (fiches Audit Qualiopi onglets).
10. **Cross-nav Airtable-style D-05** : `<Link href="/app/{entity}/{id}">` câblé systématiquement entre tous les drill-downs apprenant ↔ session ↔ produit ↔ doc.
