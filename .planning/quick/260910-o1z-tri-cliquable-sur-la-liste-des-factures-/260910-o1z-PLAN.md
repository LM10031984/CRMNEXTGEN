# Quick 260910-o1z — Tri cliquable sur la liste des factures

**Demande Laurent (2026-09-10) :** « que je puisse cliquer sur numéro, date, payeur,
montant ou statut et que ça les classe par ordre croissant / décroissant ».

## Cadrage

**Ce qui existe déjà.** La page `/app/dossiers-opco` a un tri cliquable :
`SortableTh` (`components/dossiers-opco/sortable-th.tsx`), état porté par l'URL
`?sort=&dir=`, cycle **asc → desc → remise à zéro**, flèche dans l'en-tête. On
réutilise ce composant : deux tris qui ne se comportent pas pareil dans la même
application, c'est une friction gratuite.

**Où le tri doit avoir lieu.** Côté serveur (Prisma `orderBy`), pas dans le
navigateur : la liste est paginée (50 par page), un tri côté client ne classerait
que la page affichée. 32 factures aujourd'hui, mais la pagination existe déjà.

**Colonnes non triables, et pourquoi.** « Reste » est calculé
(`amountTTC - amountPaid`) et « Relances » est un compteur d'un autre domaine :
ni l'un ni l'autre n'est une colonne SQL, les trier demanderait du SQL brut. Hors
demande, laissées telles quelles.

## Tâches

1. **Généraliser `SortableTh`** → `components/ui/sortable-th.tsx` (clé générique
   `string`). `components/dossiers-opco/sortable-th.tsx` devient un ré-export typé
   (aucun changement de comportement pour les dossiers OPCO). Ajout : un
   changement de tri **remet la pagination à la page 1** — trier en restant page 3
   affichait un extrait du milieu du nouveau classement.

2. **`lib/invoices/list-sort.ts` (module PUR, testable)** — `coerceInvoiceSort()`
   valide `?sort=`/`?dir=` venus de l'URL, `buildInvoicesOrderBy()` rend le
   `orderBy` Prisma. Pur et hors du fichier `'use server'` (un module server
   n'exporte que des fonctions async).

   | Colonne | `sort=` | `orderBy` Prisma |
   |---|---|---|
   | Numéro | `numero` | `{ number: dir }` |
   | Date | `date` | `{ issueDate: { sort: dir, nulls: 'last' } }` |
   | Payeur | `payeur` | `{ payerOrg: { legalName: dir } }` puis `{ participant: { person: { lastName: dir } } }` |
   | Montant TTC | `montant` | `{ amountTTC: dir }` |
   | Statut | `statut` | `{ status: dir }` (ordre de l'enum) |

   Départage systématique par `{ number: 'desc' }` : sans lui, deux factures du
   même jour changent de place d'un rafraîchissement à l'autre.

   Deux choix à assumer, écrits ici pour qu'ils ne se redécouvrent pas :
   - **Payeur** : le libellé affiché est dérivé (`payerOrg.legalName ?? nom de la
     personne ?? '—'`). Le tri classe donc les factures d'entreprise entre elles,
     puis celles au nom d'une personne — deux blocs, pas un alphabet unique. Un
     ordre strictement alphabétique sur le libellé exigerait un `COALESCE` en SQL
     brut, donc de dupliquer les filtres dynamiques dans une requête `$queryRaw`.
   - **Statut** : l'ordre est celui de l'enum Postgres (Brouillon, Émise, Payée,
     Partielle, En retard, Annulée, Avoir), pas un ordre d'urgence. Ce qu'on veut
     d'un clic sur « Statut », c'est regrouper ; l'urgence a déjà ses filtres et
     ses cartes KPI.

3. **`server/actions/invoices-list.ts`** — accepte `sort`/`dir`, applique
   `buildInvoicesOrderBy`. Défaut inchangé : `[{ issueDate: 'desc' }, { number: 'desc' }]`.

4. **`app/app/factures/page.tsx`** — lit `?sort=&dir=` et les passe au helper.

5. **`components/invoices/invoices-list-table.tsx`** — les 5 en-têtes deviennent
   des `SortableTh`.
